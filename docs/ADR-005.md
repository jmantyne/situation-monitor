# ADR-005: First End-to-End Validation of Multi-Model AI Governance Delivery Pipeline

**Date:** 2026-06-05
**Status:** Accepted
**Product version:** v3.1.0
**Superseded by:** — *(this ADR records a validated historical outcome; it does not govern a reversible decision)*

---

## 🇬🇧 English

### Context

Situation Monitor v3.1 was defined in BACKLOG.md as a product feature: an interactive map with a temporary inspection overlay. The feature was delivered. But v3.1 was also the first release in which a product feature was carried from backlog to release candidate entirely through a structured, multi-model AI governance pipeline — with no human implementation decisions made outside the governance framework, and no implementation begun before the specification was approved.

The pipeline exercised was:

```
Backlog
  ↓
Governance Review (Architecture · Repository · Audit · Challenge)
  ↓
Human Synthesis
  ↓
Approved Specification
  ↓
Implementation Decisions
  ↓
Execution
  ↓
Automated Testing
  ↓
Manual Validation
  ↓
Release Audit
  ↓
Release Candidate
```

Each stage produced a documented artifact. Each governance gate was held until the human operator made an explicit decision. No stage was skipped and no implementation preceded specification.

This outcome was not identified by any AI review participant during the process. The human operator identified it during the release readiness review. This ADR records what was demonstrated.

### Options Considered

**Delivery approach for v3.1:**

| Option | Description | Reason not selected |
|--------|-------------|---------------------|
| Single-model delivery | One AI model handles specification, implementation, and testing | No independent challenge; prior releases showed that scope drift and implementation assumptions accumulate without a structured review pass |
| Ad-hoc multi-model | Multiple AI models consulted informally, no structured handoff or artifact chain | No audit trail; synthesis happens implicitly; the process cannot be reproduced, taught, or audited |
| **Multi-model governance pipeline** | Sequential review by assigned roles; human synthesis between governance and execution; explicit approval gates before implementation | ✅ Selected — produces auditable artifact chain; human remains decision authority; scales to complex features |

**Pipeline stages and artifacts produced:**

| Stage | Role | Artifact |
|-------|------|----------|
| Backlog | Human | v3.1 scope definition |
| Architecture Review | ChatGPT | Product direction; Option B approved |
| Repository Review | Codex | Implementation feasibility analysis |
| Audit Review | Claude Code | Regression, security, harness, mobile UX assessment; two implementation blockers identified |
| Independent Challenge | Grok | Assumption challenge; scope and risk antithesis |
| Human Synthesis | Human | SM-V3.1-FINAL-SPECIFICATION-001 |
| Implementation Decisions | Human | SM-V3.1-IMPLEMENTATION-DECISIONS-001 (6 decisions) |
| Execution | Codex | FEAT-001 — `situation-monitor.html`, smoke tests, Playwright tests |
| Automated Testing | — | 21/21 smoke tests, 13/13 Playwright tests |
| Manual Validation | Human | Desktop Safari, iPhone Portrait, iPhone Landscape |
| Release Audit | Claude Code | Release readiness assessment; 5 documentation actions identified |
| Release Candidate | Human | v3.1.0 |

Two implementation blockers were identified during the audit review — temporary card placement strategy and race condition handling mechanism — and resolved by human decision before any implementation code was written. This is the governance gate working as designed: audit surfaces the risk, human decides, execution proceeds against resolved requirements.

### Decision

The multi-model AI governance delivery pipeline was exercised end-to-end for the first time in the delivery of Situation Monitor v3.1. The pipeline is validated as the standard delivery model for the AI Development Platform at feature scale.

The delivery produced:

| Property | Result |
|----------|--------|
| Scope compliance | Feature matched specification exactly — no localStorage, no saved cities, no 12th curated city, no new API domains |
| Implementation correctness | Generation counter, floating overlay, one-inspection-at-a-time model — all per approved decisions |
| Test coverage | Race condition coverage, mobile viewport coverage, product-identity regression coverage |
| Governance trail | Three PRs in correct sequence: SPEC-001, DECISION-001, FEAT-001 — independently auditable |
| Security posture | CSP exact-match test added; XSS audit performed; SRI unchanged; security model maintained |

### Consequences

**Positive:**

The governance model works at feature scale. Multi-model review with human synthesis produced a better-scoped result than any single model could have achieved in isolation. The two blockers identified during audit were resolved before a single line of implementation code was written — preventing a layout regression and a race condition from reaching production. This is a concrete, measurable improvement over unstructured delivery.

The audit trail is complete and independently verifiable. Anyone reading the repository can reconstruct the full decision sequence from backlog to release without any human explanation: why floating overlay was chosen over grid insertion, why the generation counter was chosen over AbortController, what each governance review found, and what the implementation delivered against those findings.

The propose → audit → human resolves blockers → implement loop is now a documented and proven pattern. It is reproducible.

**Negative / Trade-offs:**

The pipeline was human-coordinated throughout. Every output was manually transferred between tools and participants. The manual transfer bottleneck identified in CONDUCTOR-001 was present in this delivery. v3.1 validates the governance model; it does not validate automated coordination. That remains undemonstrated.

The most significant outcome of the release — that the full pipeline had been validated — was not identified by any AI review participant. It required human intervention to name. This exposes a structural gap: no review role has an explicit charter to assess what the delivery process proved about the platform that produced it. All four AI roles were scoped to the artifact, not to the pipeline. A standing retrospective question must be added to the release audit brief for all future releases.

The pipeline has only been validated at feature scale with one human operator. Validation at system scale — multiple concurrent features, reduced human bandwidth, a second human operator — remains to be demonstrated.

**Lessons Learned:**

A review process that produces technically correct artifact assessments can still miss the most significant outcome of a release if that outcome is a property of the process rather than the artifact. The mitigation is simple and must be permanent: every release audit brief must include the question — *"What does this delivery demonstrate about the platform that produced it?"* — and require an explicit answer.

The AI Development Platform now has a proven reference case. CONDUCTOR-001 describes the pipeline that v3.1 ran manually. The next development target for the platform is to reduce the manual coordination overhead that CONDUCTOR is designed to address — not by replacing the governance model, but by automating the transfer work around it.

## 🇫🇮 Suomi (alkuperäinen)

### Context

v3.1 oli backlogissa tuoteominaisuus: interaktiivinen kartta väliaikaisella inspektio-overlaylla. Ominaisuus toimitettiin. Mutta vasta release-katselmoinnin jälkeen — kun ihmisoperaattori sen osoitti — selvisi, että tämä release oli myös jotain muuta: ensimmäinen kerta, jona tuoteominaisuus vietiin läpi täydellisen, monimalligovernance-putkiston alusta loppuun ilman yhtäkään toteutuspäätöstä governance-kehyksen ulkopuolella.

Yksikään tekoälytarkastaja ei tunnistanut tätä tulosta katselmointiprosessin aikana. Ihmisoperaattori joutui osoittamaan sen erikseen release-katselmoinnissa. Tämä ADR kirjaa mitä todennettiin.

### Options Considered

Toimitusmalli v3.1:lle arvioitiin kolmen vaihtoehdon välillä: yksi tekoälymalli hoitaa kaiken, epämuodollinen monimallinen konsultointi ilman rakennetta, tai täysi monimalligovernance-putki selkeillä hyväksyntäporteilla. Kaksi ensimmäistä hylättiin: ilman itsenäistä haastajaa scope-rypistyminen oli aiemmin todistettu riski, ja ilman audit-traiilia prosessia ei voi toistaa eikä opettaa. Governance-putki valittiin.

Toteutuksen estoiksi tunnistettiin audit-katselmuksessa kaksi asiaa — väliaikaisen kortin sijoitustrategia ja race condition -käsittelymekanismi — ja ihmisoperaattori ratkaisi ne ennen kuin yhtäkään toteutusriviä kirjoitettiin. Juuri niin tämän pitääkin toimia.

### Decision

Monimalli-governance-putki ajettiin ensimmäistä kertaa päästä päähän v3.1-releasessa. Putki toimi. Tuotos oli oikein scopetettu, oikein toteutettu, kattavasti testattu ja täysin jäljitettävissä.

### Consequences

Governance-malli toimii tuoteominaisuuden kokoluokassa. Tämä ei ollut enää teoria — se on todistettu käytännössä dokumentoidulla artifact-ketjulla jota kuka tahansa voi lukea GitHubista.

Merkittävin puute: koko putki koordinoitiin manuaalisesti. CONDUCTOR-001:ssa kuvattu bottleneck — manuaalinen siirto tekoälyn suoritusympäristöstä paikalliseen repositoryyn — oli läsnä tässäkin deliveryssä. v3.1 validoi governance-mallin, ei automatisoitua koordinointia.

Tärkein havainto koko prosessista: neljä tekoälytarkastajaa kävi läpi kattavat tekniset katselmukset eikä kukaan heistä tunnistanut releasen merkittävintä tulosta. Se vaati ihmisen. Jokaisen release-katselmuksen briefissä pitää jatkossa olla pakollinen kysymys: *"Mitä tämä toimitus todistaa alustasta, joka sen tuotti?"*

### Lessons Learned

Governance-malli toimii. Bottleneck siirtyi: ennen bottleneck oli päätöksenteon laatu, nyt se on koordinaatiotyön manuaalisuus. CONDUCTOR on seuraava kehityskohde.

Tänä iltana — putkiston ensimmäisen onnistuneen ajon jälkeen — on hyvä hetki kirjata: tämä on se tulos, jonka eteen kaikki tämä työ tehtiin.
