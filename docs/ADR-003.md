# ADR-003: Automated Regression Testing — Pre-Commit Hook + Semantic Versioning

**Date:** 2026-05-27
**Status:** Accepted
**Product version:** v2.1.1
**Superseded by:** — *(supersede if CI moves to GitHub Actions or Playwright replaces the bash hook)*

---

## 🇬🇧 English

### Context

Two requirements drove this decision simultaneously.

First: version control that works **independently of GitHub**. If Claude hallucinates or begins to drift, the VERSION file and commit history provide a ground truth that cannot be overwritten by a bad AI suggestion alone.

Second: the author has a background in regression testing — several years validating C++ code in a laboratory environment as a real end-user. That experience made it clear that without an automated safety net, the risk of incremental quality degradation across many small AI-assisted commits was high.

The goal was a system that *forces* Claude to actually run regression checks rather than taking shortcuts to the result.

### Options Considered

**Quality enforcement approach:**

| Option | Reason rejected |
|--------|----------------|
| Manual checklist only | No enforcement — relies entirely on discipline; AI-assisted commits make this especially risky as Claude can skip steps under time pressure |
| GitHub Actions | Server-side CI; adds latency, requires GitHub availability, and cannot block a commit before it is pushed |
| Husky (standard pre-commit tool) | Requires Node.js and npm — incompatible with the zero-dependency single-file architecture |
| **Git pre-commit hook (bash)** | ✅ Selected — runs locally before every commit, no external dependencies, blocks bad commits at source |

**Versioning approach:**

| Option | Reason rejected |
|--------|----------------|
| Git tags only | Readable in git log but requires manual discipline; no machine-readable version file |
| GitHub Releases | GitHub-dependent; version state lives in the cloud, not in the repo |
| Manual VERSION file | Would require remembering to update on every commit — breaks under AI-assisted workflow |
| **VERSION file + hook auto-increment** | ✅ Selected — version is always current, managed automatically, works offline and independently of GitHub |

Approximately 10–15 commits were made before the hook reached its final reliable state. Manual verification was also performed after every commit — and each time, 1–2 new errors surfaced that automated checks alone had not caught.

### Decision

The hook enforces **9 checks on every commit** that touches `situation-monitor.html`:

| # | Check |
|---|-------|
| 1 | City count = exactly 11 |
| 2 | All required city IDs present |
| 3 | All 4 API endpoints referenced |
| 4 | All 4 score functions present |
| 5 | Portrait media query present |
| 6 | REGRESSION.md staged alongside HTML |
| 7 | File size < 200 000 bytes |
| 8 | No duplicate city IDs |
| 9 | No Finnish characters (ä/ö) in HTML |

Check 9 deserves special mention. The codebase evolved bilingually — Finnish and English code and commentary were intentionally mixed to test whether the automation would catch language regressions. It did. The author has 20 years of experience with ASCII/UTF character encoding challenges; implementing a robust Unicode-aware Finnish character detector (Python3, UTF-8 file read) was a deliberate quality gate that proved its value multiple times.

Versioning follows **semantic versioning (MAJOR.MINOR.PATCH)** stored in a standalone `VERSION` file. The hook auto-increments on every commit: patch for single-file changes, minor for multi-file changes. A `RELEASE_LEVEL` environment variable allows manual override for planned major or minor releases.

The `REGRESSION.md` file serves as a **formal QA log** — every version entry requires a human-written test record before the commit is accepted. This enforces the discipline of documenting *what was tested and what was found*, not just *what was changed*.

### Consequences

**Positive:**
- The last 4 consecutive commits passed all checks with zero findings — a measurable quality milestone.
- The hook has caught real errors on multiple occasions: duplicate city IDs, missing REGRESSION.md entries, Finnish characters leaking into English-only HTML, and incorrect file growth.
- Forcing REGRESSION.md to be staged alongside code changes means quality evidence travels with the code — not in a separate ticket or email chain.
- The VERSION file provides version history independent of GitHub, accessible from any git client.

**Negative / Trade-offs:**
- Getting the hook to a reliable state required approximately 10–15 commits and several iterations. The UTF-8 Finnish character check in particular went through multiple rewrites (byte-level grep produced false positives on Unicode symbols; the final Python3 solution is correct).
- The hook adds a small cognitive overhead: every HTML commit requires a REGRESSION.md update. This is a feature, not a bug — but it is friction.

### Lessons Learned

In the author's view, this is the most valuable architectural contribution of the project. It demonstrates TPM, Product Manager, and Business Development Manager thinking simultaneously:
- **TPM**: process automation, quality gates, release management
- **PM**: the product cannot ship without passing evidence of quality
- **BDM**: the system is designed to scale — a future team can trust the pipeline on day one

The project went from Hello World to a production-ready, regression-tested, versioned, CI-enforced deployment in four days — from the couch, on an iPhone, without a local development machine.

No rollbacks were needed.

## 🇫🇮 Suomi (alkuperäinen)

### Context

Halusin kehittää versiointiratkalun, joka toimii myös ilman GitHubia — jos Claude alkaa hallusinoimaan, VERSION-tiedosto ja commit-historia tarjoavat luotettavan ankkurin. Samalla halusin vanhana regressiotestaajana (useampi vuosi C++-koodin validointia laboratoriossa oikeana käyttäjänä) kehittää automaattisen regressiotestaussetin jokaiselle muokkaukselle, hotfixille ja releaselle. Ratkaisu pakotti Clauden oikeasti tekemään tarvittavat regressiotestit — ei vain oikaisemaan lopputulokseen.

### Options Considered

**Laadunvalvonnan lähestymistapa:**

| Vaihtoehto | Hylkäysperuste |
|-----------|----------------|
| Vain manuaalinen tarkistuslista | Ei pakotusta — perustuu kuriin; AI-avusteisissa commiteissa riski on erityisen korkea |
| GitHub Actions | Palvelinpuolen CI; lisää viivettä, vaatii GitHubin saatavuuden, eikä voi estää commitia ennen pushia |
| Husky (yleinen pre-commit-työkalu) | Vaatii Node.js:n ja npm:n — yhteensopimaton riippuvuuksettoman arkkitehtuurin kanssa |
| **Git pre-commit hook (bash)** | ✅ Valittu — toimii paikallisesti ennen jokaista commitia, ei ulkoisia riippuvuuksia, estää huonot commitit alkulähteellä |

**Versioinnin lähestymistapa:**

| Vaihtoehto | Hylkäysperuste |
|-----------|----------------|
| Vain git-tagit | Luettavia git-logissa, mutta vaativat manuaalista kuria; ei koneluettavaa versiotiedostoa |
| GitHub Releases | GitHub-riippuvainen; versiotila elää pilvessä, ei repossa |
| Manuaalinen VERSION-tiedosto | Pitää muistaa päivittää jokaisella commitilla — hajoaa AI-avusteisessa työnkulussa |
| **VERSION-tiedosto + hook-autoincrement** | ✅ Valittu — versio on aina ajantasainen, hallitaan automaattisesti, toimii offline ja GitHubista riippumattomasti |

Teimme noin 10–15 commitia ennen kuin hook toimi lopullisesti oikein. Claude ehdotti hookia, opetti sen rakenteen ja kertoi VERSION-tiedoston käytöstä. Manuaalinen tarkistus osoitti joka kerta 1–2 uutta virhettä, joita automaatio ei yksin ollut löytänyt.

### Decision

Isona testinä jätin suomenkielen sekä tiedostoihin että osittain keskusteluumme — FIN+ENG-koodi oli sekaisin — kunnes automaattinen regressiotestaus näytti arvonsa. Claude teki useita virheitä, mutta REGRESSION.md ja pre-commit hook toivat ne kaikki esille. Olen itse tähän erittäin tyytyväinen: kamppailtuani 20 vuotta ASCII- ja UTF-merkkien kanssa on hienoa nähdä lokalisoinnin toimivan luotettavasti.

### Consequences

Kun hook saatiin toimimaan, kaikki menee kuten automaatiossa pitää. Viimeiset 4 commitia ovat menneet täysin puhtaasti läpi. Tämä on mielestäni projektin tärkein saavutus ja näyttää ajatteluni TPM + Product Manager + BDM -lasit päässä yhtä aikaa.

### Lessons Learned

Pääsimme neljässä päivässä Hello World -tasolta tuotantovalmiiseen ratkaisuun: sohvalta, iPhonelta, ilman paikallista kehityskonetta. Commit ja liveen — ilman rollbackia.
