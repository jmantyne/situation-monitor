# ADR-004: Security Release — SRI, CSP, XSS Audit and HTTPS

**Date:** 2026-05-27
**Status:** Accepted
**Product version:** v2.1.1

---

## 🇬🇧 English

### Context

The repository was always intended to go public on GitHub — and specifically to be shared with a small group of senior Silicon Valley engineers for peer review. Before sharing, the author wanted to submit the work to scrutiny rather than present it as finished.

The trigger was unexpected: while transferring `CLAUDE.md` between GitHub and Dropbox under a different filename, Norton Antivirus blocked the file twice and flagged it as a potential hacker attack. Investigating the error messages surfaced security gaps that had not yet been addressed. The author had managed formal two-week security audits on real enterprise projects; that background made it easy to decide: address this properly.

### Options Considered

Options were evaluated both for the client side (the HTML file itself) and the GitHub repository side. The discussion covered what a motivated attacker could actually do with a public single-file dashboard: CDN supply chain attacks, clickjacking, XSS via injected data, and accidental API key exposure.

Several mechanisms were evaluated together. The decision was to implement a layered set of defences rather than rely on any single control.

### Decision

Five security controls were implemented as a single release (v2.1.0), prioritised by impact and complexity:

| Control | What it does | Priority |
|---------|-------------|----------|
| **SRI** (Subresource Integrity) | SHA-256 hash on Leaflet CSS + JS — browser blocks if CDN is tampered with | High |
| **CSP** (Content Security Policy) | `connect-src` restricts API calls to 4 known domains; `frame-ancestors 'none'` blocks clickjacking | High |
| **XSS audit** | All `innerHTML` uses verified — only numbers and hardcoded strings, no user input inserted | Medium |
| **Secret scanning** | GitHub automatic scanning confirmed active; no API keys in codebase (all chosen APIs are key-free) | Medium |
| **HTTPS** | GitHub Pages enforces HTTPS; documented explicitly in README | Baseline |

Crucially, the existing regression test suite ran against the security changes and caught integration issues immediately — demonstrating that the two architectural layers (automated testing and security controls) were aligned and mutually reinforcing.

### Consequences

**Positive:**
- Any user who downloads the file from GitHub receives a copy that is integrity-verified, CSP-protected, and free of injected secrets.
- The SRI hash on Leaflet CSS was verified correct against the live CDN. The controls work.
- The regression test suite caught security-related regressions during implementation — no manual hunting required.
- The README now includes a privacy note and SRI verification script, making the security posture transparent to any reviewer.

**The SRI hash crisis:**
The Leaflet JS SRI hash was sourced from training data rather than verified against the live CDN. The result: the hash was wrong, Leaflet JS was blocked by the browser on load, and the site was broken for all users.

The author considered removing JS SRI entirely. Instead, the conversation with Claude produced a clear explanation of *why* the hash was wrong (CDN build environment was blocked, training data was used as a shortcut), *how* to fix it (verify with `curl` and `openssl dgst`), and *why* end users are unaffected by the SRI mechanism itself — they never see it. The author ran the verification on a MacBook Pro, obtained the correct hash, and v2.1.1 restored full functionality.

**Negative / Trade-offs:**
- SRI requires the hash to be correct at all times. A wrong hash breaks the site completely and silently. This is a maintenance cost that must be accepted consciously.
- A purist might argue this level of security is over-engineering for a portfolio project. The counter-argument: anyone who downloads this file and runs it deserves the same protections they would expect from any public web resource.

### Lessons Learned

The Norton block was the best possible forcing function. It turned an abstract "we should add security" intention into a concrete, time-boxed implementation with a clear scope.

The SRI hash crisis was the most instructive failure of the project. The root cause — using training data instead of verifying against the live source — is a precise analogy for a class of AI-assisted engineering errors that will become increasingly common: *the model is confident, the answer is plausible, but it is wrong*. The mitigation is the same as for any engineering claim: **verify at the source**.

The security release also demonstrated a key principle for working with AI on technical projects: when something breaks, ask for the explanation before reaching for the workaround. Understanding *why* the hash mechanism works the way it does made the fix permanent, not a patch.

## 🇫🇮 Suomi (alkuperäinen)

### Context

Tarkoitus oli julkaista repo GitHubissa ja jakaa se muutamalle Piilaakson raskaan sarjan asiantuntijalle kommentoitavaksi. Siirrellessäni CLAUDE.md-tiedostoa GitHubista Dropboxiin eri nimellä Norton esti sen kahdesti ja varoitti hakkeri-hyökkäyksestä. Tutkin virheilmoitukset ja ne toivat pintaan puuttuvat tietoturvakontrollit. Olen aiemmissa projekteissa tilannut kaksi viikkoa kestäviä security-auditeja — se tausta helpotti päätöstä: tehdään tämä kunnolla.

### Options Considered

Kävimme Clauden kanssa läpi sekä HTML-tiedoston että GitHub-repositoryn puolen. Päätettiin ottaa käyttöön useita eri mekanismeja kerralla sen sijaan, että olisi luotettu yhteen kontrolliin.

### Decision

Toteutettiin viisi tietoturvakontrollia yhtenä releasena (v2.1.0). Regressiotestaus löysi implementointiongelmia lennossa — ja osoitti, että testausautomaatio ja tietoturvakontrollit toimivat arkkitehtuurisesti yhdessä ja olivat linjassa.

### Consequences

JS SRI hash -kriisi oli projektin tärkein yksittäinen epäonnistuminen. Hash otettiin training datasta eikä verifioitu live-CDN:stä — sivu hajosi täysin. Harkitsin SRI:n poistamista, mutta interaktio Clauden kanssa tuotti selityksen: miksi näin kävi, miten korjataan, ja miksi loppukäyttäjä ei koskaan näe SRI-mekanismia. Verifoin oikean hashin vanhalla MacBook Prollani ja v2.1.1 korjasi tilanteen.

### Lessons Learned

Jonkun mielestä tämä on over-engineeringiä portfolioprojektiin. Vastaväite: jokainen joka lataa tämän tiedoston GitHubista ansaitsee samat suojaukset kuin mistä tahansa julkisesta web-resurssista. GitHub repository on nyt turvallisempi — ja kuka tahansa voi kopioida sen itselleen ja tuoda lisäarvoa omaan työhönsä.
