# ADR-006: Governed Repeatability and Human Decision Authority — Second Validation of the Multi-Model AI Pipeline (v3.2.0 Increment 002)

**Date:** 2026-06-23
**Status:** Accepted
**Product version:** v3.2.0
**Superseded by:** — *(this ADR records a validated historical outcome; it does not govern a reversible decision)*

---

## 🇬🇧 English

### Context

Situation Monitor v3.2.0 was the configurable-city release. It was delivered in two governed increments:

- **Increment 001** established the first persistent, configurable city: a single saved point, stored separately from the curated list, with temporary inspection kept distinct from persistent monitoring.
- **Increment 002** expanded that single point into a *bounded configurable-city collection*: add, remove, restore-default, duplicate prevention, unsupported-selection fail-safe, a v2 persistence model, forward-migration of the legacy v1 value, and a dashboard capacity model — while preserving the 11 curated cities as the primary experience.

ADR-005 recorded the **first** end-to-end run of the multi-model AI governance pipeline (v3.1). The declared target of Validation #002 was different and harder: **Governed Repeatability** — whether the same pipeline holds on a *second* delivery that is not greenfield, but a data-model migration (singleton → collection) over a live persisted schema, with an existing test that asserted the *opposite* of the new requirement.

The pipeline exercised for Increment 002:

```
Backlog
  ↓
Specification
  ↓
Implementation Decisions
  ↓
ChatGPT Review   (Architecture)
Codex Review     (Repository / Implementation)
Claude Review    (Audit)
Grok Review      (Independent Challenge)
  ↓
Review Synthesis
  ↓
Human Operator Decision   ← OD-001 resolved here
  ↓
Specification Update
  ↓
Implementation
  ↓
Automated Tests
  ↓
Desktop Validation
iPhone Portrait Validation
iPhone Landscape Validation
  ↓
Release Readiness
```

Governance remained active throughout. No implementation began before the specification was approved. Every stage produced a repository artifact; nothing of decision weight remained only in chat history.

The defining event of this increment was not technical. It was a genuine **divergence between the multi-model review consensus and the human operator's decision** — surfaced as an Open Decision, resolved by human-operator authority, and justified by evidence the reviews did not have. This ADR records what that demonstrated.

### Options Considered

The reviews converged on a single unresolved gate: **how many configurable cities the curated dashboard should permit.** This was recorded as **Open Decision OD-001**.

| Option | Configurable cities | Max dashboard | Origin | Disposition |
|--------|--------------------|---------------|--------|-------------|
| **A** | 0–3 | 15 cells (1 + 11 + 3) — ragged half-filled third row on desktop | Implementation Decision 002B; the cautious synthesis position | Review recommendation |
| **B** | 0–6 | 18 cells (1 + 11 + 6) | Raised in synthesis on *observed desktop usability* | Considered |
| **Selected** | **0–6** *(useful range 2–6)* | **18 cells — clean three-row 6-column grid** | **Human Operator Decision (OD-001)** — primary scenario needs ≥2 monitored locations (home + destination); maximum confirmed usable on three devices | ✅ Selected |

The human operator **raised the configurable ceiling (3 → 6)** and recorded the minimum *useful* engagement as two monitored locations (home + destination, summer cottage, or temporary project site). The 11 curated cities remain always present in this release, so configurable cities sit **0–6 on top** of them — the "2–6" in OD-001 is the intended useful range, not a hard product floor. The reviews, scoped to per-artifact risk, optimized for the smaller number; the human operator optimized for the actual scenario *and then validated it.* The larger boundary also produced the **better** desktop layout: 18 cells is a clean 3×6 grid, whereas the review-preferred 15-cell maximum half-fills a third row.

**Dashboard capacity model (as delivered):**

| Configuration | Composition | Cells |
|---------------|-------------|-------|
| Default | Map + 11 curated | **12** |
| Maximum | Map + 11 curated + 6 configurable | **18** |
| Conceptual minimum *(reserved for a future version)* | Map + 2 monitored locations | 3 |

Reaching the 3-cell minimum requires reducing the curated set below 11 — a **user-managed curated set**, intentionally **deferred** (see Consequences).

The governance *structure* — four assigned AI roles, human synthesis, explicit human decision before any code — was held **identical** to ADR-005, which is the point of a repeatability validation:

| Stage | Role | Artifact / Finding |
|-------|------|--------------------|
| Backlog | Human operator | v3.2 configurable-city scope (`BACKLOG.md`) |
| Specification | Human operator | `SM-V3.2-INCREMENT-002-SPECIFICATION-001` |
| Implementation Decisions | Human operator | `SM-V3.2-IMPLEMENTATION-DECISIONS-001` (Decisions 001–008) |
| Architecture Review | ChatGPT | PASS with observations — MEDIUM; "largest identity risk is implementation drift" |
| Repository Review | Codex | MEDIUM–HIGH; singleton → collection migration; "would not start until UI/data-model/restore/max-layout approved" |
| Audit Review | Claude | MEDIUM; schema v2 + legacy-v1 read path, label-XSS surface, recommend map-save-only add |
| Independent Challenge | Grok | **HIGH identity risk**; antithesis — recommended tightening back toward temporary/limited, or deferring |
| Review Synthesis | Human operator | Consolidated: *approved for continued review, not yet for implementation*; **OD-001 requires human decision** |
| Human Operator Decision | Human operator | OD-001 resolved → configurable ceiling raised to 6 (spec v0.2.0) |
| Implementation | Execution | `situation-monitor.html` — bounded collection, v2 persistence, v1 migration |
| Automated Tests | — | smoke **29/29**, Playwright **24/24** |
| Cross-device Validation | Human operator | Desktop **PASS**, iPhone Portrait **PASS**, iPhone Landscape **PASS** |
| Release Readiness | Human operator | `REGRESSION.md` — v3.2.0 Increment 002 |

A further property became explicit in Increment 002: the pipeline is **role-defined and model-agnostic.** Each stage is specified by its role — Architecture, Repository / Implementation, Audit, Independent Challenge, Human Operator — not by the model that occupies it. This increment filled those seats with ChatGPT, Codex, Claude, and Grok, but the structure does not depend on that line-up: any capable model can be dropped into any role. Because the roles are now encoded in the repository artifacts, a different model line-up — or a different operator — inherits the same governance on day one. This makes the pipeline portable as well as repeatable.

### Decision

The multi-model AI governance pipeline was exercised end-to-end **a second time** for the delivery of Situation Monitor v3.2.0 Increment 002. It is validated for **governed repeatability** at feature scale — including a live data-model migration — and it is confirmed that **review evidence informs the decision while the human holds decision authority**.

| Property | Result |
|----------|--------|
| Governed repeatability | Pipeline ran end-to-end a second time; role structure unchanged from v3.1 |
| Data-model migration | Singleton configurable city → bounded collection (≤6); resolved by recorded decision, not implementation-by-assumption |
| Persistence + migration | `configurableCities.v2` schema; legacy `configurableCity.v1` value migrates forward — no Increment-001 user loses a saved city |
| Duplicate prevention | Coordinate identity, lat/lon rounded to 3 decimals (objective, testable rule) |
| Identity preservation | 11 curated cities remain primary and always present; restore-default always returns to the curated set; no new API domain; no geocoding/search UI |
| Human-operator authority | OD-001 — review recommended 0–3 configurable; the human operator approved up to 6 on cross-device evidence |
| Capacity model | Map + 11 curated + 0–6 configurable: 12 cells default, **18 cells maximum**, validated on desktop, iPhone portrait, iPhone landscape |
| Governance trail | Specification, four reviews, synthesis, implementation decisions, regression record — all repository-traceable |

### Consequences

**Positive:**

The pipeline is no longer a single validated event — it is a *repeatable* one. ADR-005 proved it could run once; Increment 002 proves it runs again, on a harder delivery, with the same role structure and the same discipline of "no implementation before specification approval."

The reviews did their job precisely by surfacing the real risks *before* any code was written: the singleton→collection migration, the persisted-schema break, the duplicate-equality ambiguity for raw map points, the label-XSS surface, and — from the independent-challenge role — the identity-drift pressure toward a generic weather dashboard. None reached production as a surprise. The audit-recommended **map-save-only** add path was adopted, closing the geocoding/CSP/XSS and identity risks in one stroke.

The human operator's override of the review recommendation was **evidence-based, not arbitrary.** A local HTTP validation loop made this possible and became a first-class governance step:

```
python3 -m http.server 8000
```

This let the human operator validate the *actual local branch* on a *real iPhone* — portrait and landscape — before commit or merge. The 18-cell maximum was confirmed readable and operational on all three devices, and it is the cleaner desktop layout of the two options. The decision to allow six configurable cities was therefore a *measured* decision, recorded as OD-001 with its evidence, not a preference asserted over the reviewers.

Repository Truth was preserved. Every stage left an artifact a reader can reconstruct without any human narration: why the ceiling moved to six, what each model found, what the migration did, what was tested and what passed. The pre-commit guardrails (curated `CITIES` held at exactly 11) protected product identity mechanically while the collection model was added around them. *(The role of HARNESS as an active governance stage is drawn out in Lessons Learned.)*

**Negative / Trade-offs:**

The delivery was still human-coordinated end to end. Every artifact was moved between tools and participants by hand — the manual-transfer bottleneck noted in ADR-005 (CONDUCTOR-001) was present again. Increment 002 validates the governance model and its repeatability; it does **not** validate automated coordination, and it remains single-operator.

A structural observation deserves recording: **multi-model review converges on caution.** All four models, scoped to risk, recommended the smaller boundary or argued to defer. That conservatism is correct as a *risk signal* and wrong as a *product decision* — and the only thing that resolved the gap was embodied, cross-device validation by the human. Review consensus is evidence about risk; it is not a substitute for product judgment exercised against the real device.

Increment 002 also revealed a future capability and **deliberately deferred it.** The delivered model is `Map + 11 curated + 0–6 configurable`. The natural next capability is a **user-managed curated set** — letting the user *reduce, replace, or customize* the curated 11, down toward the Map + 2 minimum the capacity model already reserves. This was intentionally not built; it is recorded as a backlog pointer, not inflated into premature specification *(see Lessons Learned — Occam's Razor as a governance principle)*.

### Lessons Learned

The single most important lesson of this increment, stated plainly:

> **The review process provides evidence. The human makes the decision. Evidence can overrule the consensus assumption — when the human goes and gets better evidence.**

The initial concern was that more configurable cities would dilute the curated, calm identity of the dashboard. The actual validation — Desktop PASS, iPhone Portrait PASS, iPhone Landscape PASS — showed the 18-cell layout remained usable, and in fact tidier on desktop than the cautious option. The assumption lost to the measurement. What made this legitimate rather than reckless was that the human operator produced repository evidence (OD-001 resolution + regression record) for the decision, exactly as a reviewer would be required to.

Four further lessons:

1. **Repeatability is a property worth validating on purpose.** ADR-005 noted that no review role is chartered to assess what a delivery proves about the platform that produced it. Validation #002 set that question *in advance* — "does this strengthen or weaken governed-repeatability evidence?" — and the answer is that the pipeline held on a harder, migration-bearing delivery. The standing retrospective question from ADR-005 worked.

2. **Local HTTP validation is governance, not convenience.** `python3 -m http.server 8000` turned "I think it'll be fine" into "I validated the branch on the device before merge." Cross-device evidence is what separates a human-operator *decision* from a mere *preference*.

3. **HARNESS is a governance stage, not a document.** The pipeline requires implementation instructions to pass explicitly through HARNESS → Specification → Reviews → Implementation before execution begins. Increment 002 proved why that ordering is a control and not a formality: when the AI in the Architecture role drafted the execution instructions for the Implementation stage, the HARNESS stage was initially omitted from the chain. The human operator caught the omission and halted execution before any implementation began; HARNESS was restored to the chain. The omission was instructive precisely because HARNESS, sitting among the repository's documents, *reads* like a reference one could skip — but it is a stage, and skipping it routes execution around the accumulated guardrails. Tellingly, the omission arose inside an AI role and was caught by the human operator — the same division of labour this ADR documents. A governance control is only effective when it is treated as an active process stage, not a passive document.

4. **Occam's Razor is a governance principle.** A recurring question across the release was "does this require a new document?" The working rule: a new document is justified only if it (a) adds capability, (b) preserves important learning, or (c) improves traceability. Otherwise repository complexity grows without adding governance value. This is why the user-managed curated set stayed in the backlog — and why ADR-006 itself was written: it preserves the human-override-on-evidence pattern, the most teachable outcome of the release.

## 🇫🇮 Suomi (alkuperäinen)

### Context

v3.2.0 oli muokattavien kaupunkien release, toimitettuna kahdessa hallitussa incrementissä. Increment 001 toi yhden pysyvän muokattavan kaupungin. Increment 002 laajensi sen rajatuksi muokattavien kaupunkien kokoelmaksi: lisää, poista, palauta oletukset, duplikaattiesto, v2-persistenssi ja vanhan v1-arvon migraatio — säilyttäen 11 kuratoitua kaupunkia ensisijaisena kokemuksena.

ADR-005 kirjasi putkiston **ensimmäisen** läpiajon (v3.1). Validation #002:n julistettu kohde oli vaikeampi: **hallittu toistettavuus** — pitääkö sama putki, kun kyseessä ei ole tyhjältä pöydältä rakennettu ominaisuus vaan datamallin migraatio (singleton → kokoelma) elävän persistoidun skeeman päällä.

Tämän incrementin määräävä hetki ei ollut tekninen. Se oli aito **ero monimallisen review-konsensuksen ja ihmisoperaattorin päätöksen välillä** — nostettiin Avoimeksi Päätökseksi, ratkaistiin ihmisoperaattorin auktoriteetilla ja perusteltiin evidenssillä, jota revieweillä ei ollut.

### Options Considered

Reviewit tiivistyivät yhteen ratkaisemattomaan porttiin: **kuinka monta muokattavaa kaupunkia kuratoitu dashboard sallii.** Tämä kirjattiin **Avoimena Päätöksenä OD-001**.

- **Vaihtoehto A — 0–3 kaupunkia (max 15 solua):** Implementation Decision 002B; varovainen synteesikanta. Työpöydällä vajaa kolmas rivi. *Review-suositus.*
- **Vaihtoehto B — 0–6 kaupunkia (max 18 solua):** nostettu synteesissä havaitun työpöytäkäytettävyyden perusteella.
- **Valittu — 0–6 kaupunkia (mielekäs väli 2–6), max 18 solua:** **Ihmisoperaattorin päätös (OD-001).** Mielekäs skenaario vaatii vähintään kaksi seurattavaa paikkaa (koti + kohde). Maksimi varmistettiin käytettäväksi kolmella laitteella.

Ihmisoperaattori **nosti kattoa (3 → 6)** ja kirjasi 2:n pienimmäksi *mielekkääksi* käytöksi. 11 kuratoitua kaupunkia pysyy aina läsnä tässä releasessa, joten muokattavat ovat **0–6 niiden päälle** — "2–6" on tarkoitettu mielekäs väli, ei kova tuotelattia. Isompi raja antoi myös **siistimmän** layoutin: 18 solua = puhdas 3×6, kun review'n suosima 15 jättää kolmannen rivin vajaaksi.

**Dashboard-kapasiteettimalli (toimitettu):**
- Oletus: kartta + 11 kuratoitua = **12 solua**
- Maksimi: kartta + 11 kuratoitua + 6 muokattavaa = **18 solua**
- Käsitteellinen minimi *(varaus tulevalle versiolle)*: kartta + 2 paikkaa = 3 solua

3 solun minimi edellyttää kuratoitujen vähentämistä alle 11:n — **käyttäjän hallitsema kuratoitu setti**, joka on tarkoituksella **lykätty** (ks. Consequences).

Governance-*rakenne* pidettiin **identtisenä** ADR-005:n kanssa: neljä roolitettua AI-tarkastajaa (ChatGPT/Arkkitehtuuri, Codex/Repository, Claude/Audit, Grok/Haastaja), ihmissynteesi ja nimenomainen ihmispäätös ennen yhtäkään koodiriviä. Juuri se on toistettavuuden validoinnin pointti.

Increment 002:ssa tuli eksplisiittiseksi vielä yksi ominaisuus: putki on **rooliperustainen ja malliagnostinen.** Jokainen vaihe määritellään roolinsa kautta — Arkkitehtuuri, Repository / Implementation, Audit, Itsenäinen haastaja, Ihmisoperaattori — ei sen mallin kautta joka roolin täyttää. Tässä incrementissä paikat täyttivät ChatGPT, Codex, Claude ja Grok, mutta rakenne ei riipu tästä kokoonpanosta: mikä tahansa kyvykäs malli voidaan pudottaa mihin tahansa rooliin. Koska roolit on nyt koodattu repository-artefakteihin, eri mallikokoonpano — tai eri operaattori — perii saman governancen ensimmäisestä päivästä. Tämä tekee putkesta siirrettävän, ei vain toistettavan.

### Decision

Monimalli-governance-putki ajettiin päästä päähän **toista kertaa** Increment 002:ssa. Se on validoitu **hallitun toistettavuuden** osalta — datamallin migraatio mukaan lukien — ja on vahvistettu, että **review-evidenssi ohjaa päätöstä, mutta ihminen pitää päätösvallan.** Tulos oli oikein scopetettu, migraatio hoidettu taaksepäin yhteensopivasti (`configurableCities.v2`, vanha `configurableCity.v1` migroituu), duplikaatit estetty koordinaatti-identiteetillä, ja 18-solun maksimi validoitu kolmella laitteella. Automaatio: smoke 29/29, Playwright 24/24.

### Consequences

Putki ei ole enää yksittäinen validoitu tapahtuma vaan **toistettava.** Reviewit tekivät tehtävänsä juuri nostamalla todelliset riskit esiin *ennen* koodia: singleton→kokoelma-migraatio, skeeman rikkoutuminen, duplikaattisäännön epämääräisyys raakapisteille, label-XSS, ja identiteetin liukuminen kohti geneeristä sääsovellusta. Yksikään ei tullut yllätyksenä tuotantoon. Audit-suosittama **map-save-only**-lisäyspolku otettiin käyttöön, mikä sulki geokoodaus-, CSP-, XSS- ja identiteettiriskit kerralla.

Ihmisoperaattorin poikkeaminen review-suosituksesta oli **evidenssipohjainen, ei mielivaltainen.** Paikallinen HTTP-validointi teki tämän mahdolliseksi ja siitä tuli ensiluokkainen governance-vaihe:

```
python3 -m http.server 8000
```

Tämä antoi validoida *oikean paikallisen branchin* *oikealla iPhonella* — pysty ja vaaka — ennen committia tai mergeä. Repository Truth säilyi: jokainen vaihe jätti artefaktin, josta lukija rekonstruoi miksi katto nousi kuuteen. *(HARNESSin rooli aktiivisena governance-vaiheena avataan Lessons Learned -osiossa.)*

Rajoitteet: delivery oli yhä ihmiskoordinoitu päästä päähän — ADR-005:n manuaalisen siirron pullonkaula (CONDUCTOR-001) oli läsnä taas. Tämä validoi governance-mallin ja sen toistettavuuden, ei automatisoitua koordinointia, ja se on yhä yhden operaattorin malli.

Rakenteellinen havainto: **monimallinen review konvergoi varovaisuuteen.** Kaikki neljä mallia suosittelivat pienempää rajaa tai lykkäämistä. Se on oikein *riskisignaalina* ja väärin *tuotepäätöksenä* — eron ratkaisi vain ihmisen ruumiillinen, laitekohtainen validointi.

Increment 002 paljasti myös tulevan kyvykkyyden ja **lykkäsi sen tarkoituksella:** käyttäjän hallitsema kuratoitu setti (vähennä, korvaa, kustomoi 11 kuratoitua — kohti kapasiteettimallin kartta + 2 -minimiä). Tätä ei rakennettu; se kirjattiin backlog-osoittimena, ei ennenaikaisena spesifikaationa *(ks. Lessons Learned — Occamin partaveitsi)*.

### Lessons Learned

Tärkein oppi, suoraan sanottuna: **Review tuottaa evidenssin. Ihminen tekee päätöksen. Evidenssi voi kumota konsensuksen oletuksen — kun ihminen menee hakemaan paremman evidenssin.**

Alkuhuoli oli, että useampi muokattava kaupunki hajottaisi kuratoidun, rauhallisen ilmeen. Todellinen validointi — Desktop PASS, iPhone Portrait PASS, iPhone Landscape PASS — osoitti 18-solun layoutin pysyvän käytettävänä, työpöydällä jopa siistimpänä kuin varovainen vaihtoehto. Oletus hävisi mittaukselle. Se mikä teki tästä legitiimin eikä holtittoman: ihmisoperaattori tuotti päätökselle repository-evidenssin (OD-001 + regression), aivan kuten tarkastajaltakin vaadittaisiin.

Neljä lisäoppia:

1. **Toistettavuus kannattaa validoida tarkoituksella.** Validation #002 asetti kysymyksen etukäteen — "vahvistaako vai heikentääkö tämä hallitun toistettavuuden evidenssiä?" — ja putki piti vaikeammassa, migraation sisältävässä deliveryssä. ADR-005:n pysyvä retrospektiivikysymys toimi.

2. **Paikallinen HTTP-validointi on governancea, ei mukavuutta.** `python3 -m http.server 8000` muutti "kai se on kunnossa" -ajattelun muotoon "validoin branchin laitteella ennen mergeä." Laitekohtainen evidenssi erottaa ihmisoperaattorin *päätöksen* pelkästä *mieltymyksestä*.

3. **HARNESS on governance-vaihe, ei dokumentti.** Putki vaatii, että toteutusohjeet kulkevat eksplisiittisesti HARNESS → Specification → Reviews → Implementation ennen suoritusta. Increment 002 osoitti, miksi tämä järjestys on kontrolli eikä muodollisuus: kun Arkkitehtuuri-roolissa toimiva AI laati Implementation-vaiheen suoritusohjeet, HARNESS-vaihe jäi aluksi pois ketjusta. Ihmisoperaattori havaitsi puutteen ja pysäytti suorituksen ennen kuin yhtäkään toteutusriviä kirjoitettiin; HARNESS palautettiin ketjuun. Puute oli opettavainen juuri siksi, että HARNESS repositoryn dokumenttien joukossa *näyttää* ohitettavalta viittaukselta — mutta se on vaihe, ja sen ohittaminen kiertää kertyneet guardrailit. Kuvaavaa on, että puute syntyi AI-roolin sisällä ja sen havaitsi ihmisoperaattori — juuri se työnjako, jonka tämä ADR dokumentoi. Kontrolli on tehokas vain aktiivisena prosessivaiheena, ei passiivisena dokumenttina.

4. **Occamin partaveitsi on governance-periaate.** Toistuva kysymys releasen läpi: "vaatiiko tämä uuden dokumentin?" Työsääntö: uusi dokumentti on perusteltu vain jos se (a) tuo kyvykkyyttä, (b) säilyttää tärkeän opin, tai (c) parantaa jäljitettävyyttä. Muuten repository-monimutkaisuus kasvaa ilman governance-arvoa. Siksi käyttäjän hallitsema kuratoitu setti jäi backlogiin — ja siksi ADR-006 kirjoitettiin: se säilyttää ihmisen evidenssipohjaisen päätöksen kuvion, releasen opettavaisimman tuloksen.
